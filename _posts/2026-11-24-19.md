這篇從工程知識管理的角度說明 QMD 這個本機文件搜尋引擎適合多大、哪些類型的資料，以及怎麼建出查得準的知識庫。另外也說明一份動輒數百頁的 PDF 手冊為什麼需要另一種工具，以及 PageIndex 的做法和 QMD 差在哪裡。

- **為什麼需要這類工具**：工程知識分散在設計文件、維運手冊、事故檢討、會議紀錄、程式碼和廠商 PDF 裡。人找不到，AI 代理也只能一個一個檔案翻。檢索工具先把資料整理成索引，查詢時只交出相關的段落或頁面。
- **QMD 解決的問題**：大量零散的文字檔「找得到」。工程查詢有兩種，一種是精確字串（錯誤碼、函式名），一種是模糊問題（為什麼當初這樣設計）。QMD 把關鍵字、語意和模型重排序結合起來，兩種都能應付。
- **PageIndex 解決的問題**：少數又長又有章節結構的 PDF，例如技術手冊、規格書、法規文件。它不把文件切塊，而是建一份目錄樹，讓語言模型像人翻目錄一樣找到該讀的頁面。
- **兩者都不解決的問題**：文件過時、沒人寫、權限控管。這些仍然要靠人。
- **QMD 值得用的情況**：幾百到幾千份文字文件散在多個 repo 和資料夾，內容不想送上雲端，團隊已經在用 Claude Code 這類代理。
- **不太值得的情況**：只有幾十份文件；需要多人權限與共同寫入；資料主要是掃描檔或線上服務裡的內容。
- **成效的關鍵**：QMD 要看分類（collection）、情境描述（context）、metadata 這三層組織做得好不好。中文團隊還要換掉預設的嵌入模型，並用自己的資料實測。

## QMD 是什麼、做什麼用

QMD 全名 Query Markup Documents，是一個命令列搜尋工具，以 MIT 授權開源。它掃描你指定的資料夾，把內容存進一個本機的 SQLite 索引檔，提供三種查法：

- **search**：純 BM25 關鍵字搜尋。速度快，不需要語言模型。
- **vsearch**：純向量語意搜尋。依意思找文件，不靠字面比對。
- **query**：混合模式。先由一個小模型把問題改寫成其他說法，原始問題和改寫後的問題都同時跑關鍵字與向量搜尋。接著用 RRF（Reciprocal Rank Fusion）合併排名，最後交給重排序模型評分。這是品質最好的模式。

混合模式有一個對工程文件很重要的設計。排名最前面的一到三筆，原始檢索分數佔 75%、重排序模型佔 25%；排名越後面，重排序的比重越高。這樣可以避免重排序模型把「字面完全命中」的文件擠下去。查一個特定錯誤碼時，你最想看到的就是那個錯誤碼出現的地方。

預設的三個模型都是 GGUF 格式，第一次使用時自動下載：嵌入模型約 300MB，重排序模型約 640MB，查詢改寫模型約 1.1GB。執行環境需要 Node.js 22 以上或 Bun，macOS 另外需要 Homebrew 版的 SQLite。沒有 GPU 也能跑，在 CPU 上可以關掉重排序換取速度。

## QMD 在工程上可以怎麼用

QMD 從設計之初就把 AI 代理當成使用者。它有四種接法：

1. **命令列**：代理直接下指令，輸出可以是 JSON 或純檔案清單，方便接著處理。
2. **MCP 伺服器**：提供搜尋、取文件、批次取文件、查索引狀態、查 metadata 等工具。Claude Desktop、Claude Code 和其他支援 MCP 的客戶端都能接，專案也提供 Claude Code 外掛。
3. **HTTP 伺服器**：讓模型常駐記憶體，多個客戶端共用，不必每次重新載入。
4. **Node.js / Bun SDK**：把 QMD 嵌進自己的內部工具。

放到工程團隊的日常，幾個典型用法是：

- **值班與排障**：把 runbook 和事故檢討建成索引。告警出現時，用錯誤碼或服務名查過去的處理紀錄，這正是關鍵字搜尋擅長的場景。
- **新人上手**：「這個服務為什麼用訊息佇列，而不是直接呼叫？」這類問題沒有固定關鍵字，要靠語意搜尋從架構決策紀錄（ADR）和設計文件裡找答案。
- **讓代理寫程式前先查規範**：代理改動某個模組前，先查內部的 API 文件、編碼規範和相關 ADR，再動手。這比每次把整個 docs 資料夾塞進上下文省很多。
- **追溯決策**：在會議紀錄和技術討論的逐字稿裡，找出某個決定是何時、為何做出的。
- **程式碼語意搜尋**：用「哪裡處理重試邏輯」這種說法找程式碼，而不只是 grep 函式名。

如果要把 HTTP 伺服器開給整個團隊共用，有一點必須知道：README 明白寫著這些端點**沒有身分驗證**。預設只綁定本機位址，也有阻擋 DNS rebinding 的來源檢查。一旦對外開放，就得自己在前面加一層驗證。

## 多大的資料用得上 QMD

README 沒有寫明資料量上限，但從設計可以看出適用範圍：

- **儲存方式**：整個索引是單一 SQLite 檔。文件切成約 900 token 一塊，前後重疊 15%，再做向量化。重新索引時只處理有變動的檔案，README 的範例是一個 wiki 有 340 份未變動、2 份更新。
- **大型語料**：嵌入時可以限制每批的文件數和記憶體用量，給語料大或資源有限的機器使用。
- **篩選的門檻**：帶 metadata 條件的向量搜尋，符合條件的區塊在 20,000 個向量以內時會精確掃描。超過時改成先多抓再過濾，回傳的筆數可能少於要求。
- **單一檔案**：批次取回文件時，命令列預設跳過大於 64KB 的檔案，MCP 工具的預設值更低，是 10,240 bytes。很長的逐字稿仍然搜得到，因為已經切塊；但代理要讀回原文時，應該改用指定行數範圍的方式讀取。

換算成判斷標準：

- **太小**：幾十份 Markdown，代理直接列目錄、讀檔就夠了，多架一套索引的好處有限。
- **剛好**：幾百到幾千份文件，散在多處，已經沒人記得哪份文件寫了什麼。README 的 metadata 範例輸出用的就是 480 份和 2,100 份文件的規模。
- **太大或太複雜**：需要分散式搜尋、細緻的權限控管、多人同時寫入時，這個單機工具就不是正確答案，應該考慮伺服器端的企業搜尋方案。

## 什麼類型的資料適合 QMD

專案描述列出的對象是 Markdown 筆記、會議逐字稿、技術文件和知識庫。對工程團隊來說，大致是：

- 架構決策紀錄與設計文件
- 維運手冊與事故檢討
- 會議紀錄、技術討論逐字稿
- API 文件、內部 wiki
- 原始碼

**預設只索引 `.md` 檔**，每個 collection 都可以自訂要收哪些檔案。程式碼方面，TypeScript、JavaScript、Python、Go、Rust 可以啟用語法樹切塊，依類別、函式、import 的邊界切分，避免把一個函式從中間切斷。

QMD 只讀檔案系統上的文字檔。放在線上文件服務裡的資料，要先匯出成檔案；其他格式的文件，比較穩當的做法是先轉成 Markdown。SDK 也提供 collection processor 機制，可以把來源檔轉成 Markdown 索引文件。

Markdown 切塊時，會優先在標題、程式碼區塊邊界、段落處斷開，而不是硬切在固定字數，程式碼區塊也會盡量保持完整。所以**文件寫得越有結構**，標題分明、一段講一件事，搜尋品質就越好。

**中文資料要特別處理。** 預設的嵌入模型 embeddinggemma-300M 以英文為主，README 也坦承它對中日韓文的支援有限，建議改用支援 119 種語言的 Qwen3-Embedding-0.6B。換模型之後必須全部重新嵌入，因為不同模型產生的向量不能混用。另外，README 沒有說明關鍵字搜尋如何處理中文斷詞。以中文文件為主的團隊，導入前應該先拿自己的資料試查。

## 怎麼用 QMD 建立一個查得準的知識庫

把資料夾丟進去只是開始，真正決定品質的是下面四層。

**第一層：collection，依資料性質分開。** 每個 collection 對應一個資料夾和一組檔案規則。設計文件、runbook、會議紀錄、程式碼可以各建一個，查詢時可以指定範圍，也可以合併查。容易干擾結果的 collection 可以設成預設不納入，需要時再點名查詢。QMD 也內建排除 node_modules、.git、dist、build 等目錄。

**第二層：context，告訴搜尋引擎每個資料夾是什麼。** README 特別強調這是 QMD 的關鍵功能。你可以替整個 collection 或其中的子路徑寫一句描述，例如「支付服務的維運手冊」或「2024 年以前的舊架構文件，部分已過時」。這些描述呈樹狀結構，路徑越具體越優先。搜尋結果會連同描述一起回傳，代理就能分辨一份文件是現行規範還是歷史紀錄。工程知識最常見的錯誤，就是把過時文件當成現況，這一層正好對症。

**第三層：metadata，讓文件可以被篩選。** 在文件開頭的 frontmatter 加上 QMD 專用的 metadata 區塊，值可以是字串、數字、布林值或簡單陣列，例如所屬服務、負責團隊、狀態（草稿、已發布、已廢棄）、優先度。查詢時就能下條件，例如「只找已發布、標記為 payment 的文件」。QMD 也能列出索引裡實際有哪些欄位和值，讓你照實際資料寫條件，不用猜。遇到型別衝突，例如有些文件的 priority 寫數字、有些寫 high，它會如實列出，不會自動合併。對多人維護的知識庫來說，這能幫你發現標記習慣不一致的地方。

**第四層：保持同步。** 每個 collection 可以設定一個在重新索引前執行的指令，最常見的是 git pull。文件 repo 更新後，重新索引會先拉最新版本。也可以在專案目錄裡建立專屬索引，讓設定跟著專案走。不過，別人 repo 裡附帶的設定預設不受信任：更新指令、指向專案外的路徑、自訂模型這三類設定，都要你手動核准才會生效。這很合理，沒人想 clone 一個 repo 就自動執行陌生人寫的 shell 指令。

## 怎麼知道 QMD 真的有用

導入搜尋工具最怕「感覺有用」。QMD 內建基準測試：你準備一組「問題對應到應該找到的文件」，它用關鍵字、向量、混合、完整流程四種方式各跑一次，算出精確率、召回率等指標。README 提到範例測試集的典型結果，大約是關鍵字 0.50、向量 0.70、混合與完整流程接近 1.00。

工程團隊比較實際的做法，是蒐集新人最常問的二三十個問題，寫成自己的測試集。換嵌入模型、調整 context 或 metadata 之後跑一次，就知道品質是變好還是變差。查詢時也能要求列出每筆結果的計分明細，追查某份文件為什麼排第一。

## 長篇 PDF 是另一個問題：PageIndex 的做法

QMD 擅長的是「很多份、每份不長」的文字檔。工程團隊還有另一類資料，形狀完全不同：晶片 datasheet、廠商的技術手冊、產業標準規格書、法規與合規文件。這類資料通常是 PDF，一份就幾百頁，答案往往要從章節脈絡推出來，例如「第 7 章的限制條件適用於附錄 B 的哪一種設定」。把它切成 900 token 的小塊再比對相似度，很容易把脈絡切斷。

[PageIndex](https://github.com/VectifyAI/PageIndex) 走的是另一條路。它的主張是：向量檢索找的是「相似」，但檢索真正需要的是「相關」，而判斷相關需要推理。所以它不用向量資料庫，也不切塊，分兩步運作：

- **建索引**：替每份 PDF 產生一棵樹狀索引，像是寫給語言模型看的目錄，包含標題、頁碼範圍和摘要。樹的結構來自 PDF 本身的版面，不靠語言模型；模型只負責寫各節點的摘要並修整結構。
- **查詢**：讓語言模型沿著這棵樹推理，判斷該翻到哪一節，讀那幾頁，再回答。答案可以附上頁碼引用。

這個主張用來批評「純向量」的系統很有道理，但套到 QMD 身上要打折扣。QMD 本來就不是純向量檢索：它有關鍵字搜尋，也有語言模型重排序。兩者真正的差別在於檢索單位：QMD 找的是文字片段，PageIndex 找的是文件裡的章節與頁面。

**多大的資料用得上。** PageIndex 是以「單份長文件」為單位思考的。專案公布的本機測試裡，9 頁到 1,098 頁的文件建索引大約花 13 秒到 4.5 分鐘；建樹的成本約每頁 0.001 美元，一本 1,000 頁的教科書約一美元多，建一次就能一直重複使用。它也拿「每次都把整份 PDF 丟給模型」來比較：在兩種做法答案相同的文件上，整份丟進去的成本在 52 頁時是它的 2.1 倍，420 頁時是 16.6 倍；到 805 頁，文件已經塞不進模型的上下文。換句話說，幾十頁的文件直接讀也行，上百頁之後才明顯需要它。專案另外宣稱在 FinanceBench 財報問答測試上達到 98.7% 準確率，這是團隊自己公布的數字，用在工程文件上的效果仍然要自己驗證。

**什麼類型的資料。** 開源的本機版只處理含文字層的 PDF。掃描檔、以圖為主的文件要用他們的雲端版，雲端版會逐頁以視覺方式讀取，不經 OCR。collection 與 metadata、資料夾管理、MCP 伺服器也都只在雲端版提供。專案列出的適用對象包括財報、法律文件、監管申報、技術手冊、醫學文獻和教科書。對工程團隊來說，對應的就是廠商手冊、規格書和合規文件。

**怎麼建、怎麼用上。** 用 Python 套件把 PDF 送進去建樹，索引存在本機資料夾，可以只看樹狀結構，也可以取出特定頁的內容。查詢有兩條路：一是交給 PageIndex 自己的代理，用你指定的語言模型找頁面並寫答案，可以續問，也可以跨多份文件問；二是把它的工具交給你既有的代理，支援 OpenAI Agents SDK、Anthropic SDK、Claude Agent SDK，其他框架可以直接用一般的 Python 函式。

**最需要注意的一點：本機版並不等於資料不出門。** 建索引時要用語言模型寫摘要，查詢時要用語言模型推理，這兩步都會呼叫你設定的模型供應商，可以是 OpenAI、Anthropic、OpenRouter，或透過 Claude Code 使用 Claude 訂閱。PageIndex 的「本機」指的是索引存放在你的機器上，文件內容仍會送到模型供應商。這和 QMD 預設三個模型都在本機執行，是性質完全不同的兩件事。不能上雲的內部文件，選工具前要先確認這一點。

兩者在工程知識管理裡比較像分工，不是二選一：

- **QMD**：管 repo 裡大量的 Markdown、程式碼、會議紀錄、runbook，要求本機執行、精確字串也要查得到。
- **PageIndex**：管少數長篇 PDF，答案依賴章節結構，而且需要回答附頁碼出處。
- 硬把長篇 PDF 轉成 Markdown 丟進 QMD 也做得到，但頁碼和章節脈絡會流失多少，要看轉檔品質。用 QMD 內建的評測拿實際問題比一比，比憑感覺判斷可靠。

## 能不能解決問題、值不值得用

QMD 能解決的是「知識存在，但找不到」。它做得很細：混合搜尋、保護精確命中的排名設計、依文件結構切塊、metadata 篩選、內建評測，特別適合工程文件這種精確字串和模糊問題並存的資料。資料預設不離開本機，也讓它能用在不能上傳雲端的內部文件上。

它解決不了的是「知識本身有問題」。它不會替你寫文件，不會判斷哪份已經過時，也不是會自己記住對話的記憶系統，代理要主動去查才會用到它。它的成效直接取決於知識庫整理得多清楚：哪些資料夾放什麼、哪份文件還有效、屬於哪個服務。整理得好，不管有沒有 AI，知識管理都會變好；整理得不好，再強的模型也只會很有效率地找到過時的文件。

還有一點要寫進團隊規範：QMD 的「完全本機」只是預設，不是唯一選項。它支援把嵌入交給外部的 OpenAI 相容服務，也支援用 TypeSafe 的雲端服務做重排序。啟用這些選項後，文件內容就會送出本機。PageIndex 則從一開始就需要外部語言模型。

結論是：如果團隊有幾百份以上的文字文件、已經在用 AI 代理寫程式或排障、願意花時間設計 collection 和 context，QMD 很值得試，而且試的成本不高。如果卡住團隊的是幾份幾百頁的廠商手冊或規格書，而且內容可以交給模型供應商處理，PageIndex 的目錄樹做法更對症。如果文件量很少，或真正的問題是沒人寫、沒人更新文件，先處理那個問題比較實際。
