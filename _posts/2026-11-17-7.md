這篇用淺白的方式介紹 Hugging Face 和 OpenRouter 各自在做什麼，再說明兩家合作之後，想用開放權重模型的人能省下哪些麻煩，又有哪些地方要留意。

**重點整理：這次合作解決了什麼問題**

- **原本的麻煩**：開放模型很多，提供運算的供應商也很多。要選哪一家、哪家比較便宜、哪家今天變慢或當機，原本都得自己判斷。
- **合作後的做法**：用 Hugging Face 的 token 和同一套 API，就能叫用 Hub 上有供應商提供服務的開放模型。每次請求由 OpenRouter 依照即時的價格、速度和穩定度挑選供應商。第一家失敗，就自動換下一家。
- **價格**：照供應商原價計費，Hugging Face 不另外加價。
- **要注意的改變**：叫用語言模型時，不能再搭配自己申請的供應商金鑰。

## Hugging Face 是什麼

可以把 Hugging Face 想成 AI 模型的大型圖書館。

它在 2016 年成立，一開始做的是聊天機器人 App。後來團隊把自己寫的 Transformers 函式庫開源，這套工具大受歡迎，Hugging Face 也漸漸成為大家存放、分享 AI 模型的地方。現在幾乎所有重要的開放權重模型推出時，都會發佈在 Hugging Face Hub 上。

不過圖書館只負責「收書」。書放在架上，不代表你能馬上讀。模型也一樣，下載之後還需要強大的顯示卡才跑得動。所以 Hugging Face 另外提供 Inference Providers 服務：你不必自備硬體，透過網路請別家的伺服器幫你執行模型。

## OpenRouter 是什麼

OpenRouter 比較像叫車 App。

叫車時你不會指定哪一位司機。App 會看誰離你近、誰的評價好，自動幫你派車。司機臨時取消，App 會再派下一位，你不用重新叫一次。

OpenRouter 做的是同樣的事，只是派的是「執行 AI 模型的供應商」。同一個開放模型，可能有好幾家公司在自己的機房裡提供服務，價格和速度都不一樣。OpenRouter 目前串接 80 多家供應商、600 多個模型，每月處理超過 800 兆個 token，使用者超過一千萬人。流量這麼大，它能隨時量到每一家供應商的實際表現。

它最近也改寫了派車邏輯。以前主要看誰標價最低，現在會綜合價格、速度和穩定度來挑。某家供應商變慢或開始出錯，流量會先移開，等它恢復再導回去。根據 OpenRouter 自己的量測，新的路由方式讓容量不足的錯誤減少 46%，第一個字出現的時間縮短 16.9%，吞吐量提升 16.3%。

## 為什麼開放模型需要「派車」

開放模型這一年的用量成長得非常快。在 OpenRouter 上，開放權重模型在 2025 年 10 月只占 26.8% 的 token 用量，到 2026 年 9 月底已經是 71.7%，7 月時最高到 77.5%。同一段期間，開放模型的每週用量成長超過 60 倍，閉源模型則將近 10 倍。這週 OpenRouter 上用量最大的模型也是開放模型 DeepSeek V4.1 Flash 1017，用了 59.2 兆個 token。

便宜是主要原因之一。開放模型平均每百萬輸入 token 約 0.28 美元，輸出約 1.62 美元。閉源模型則是 1.27 美元和 6.36 美元，價差大約四倍。

開放模型在最難的測驗上還是落後。在 Artificial Analysis 智慧指數上，最好的開放模型 Kimi K3.1 Pro 得 46 分，Claude Fable 5.2 得 65 分。但完成一項任務的成本，前者約 3.68 美元，後者約 26.54 美元，大概只要七分之一。對很多日常工作來說，這樣的取捨很划算。

用的人越多，供應商也越多，「該找哪一家」就越需要有人代為處理。

## 這次合作改變了什麼

Hugging Face 把 Inference Providers 原本自己寫的路由器，換成 OpenRouter 的。從現在開始，語言模型的請求都會經過 OpenRouter 派送，原本寫好的程式不用改。

具體的差別有幾個：

- **失敗會自動重試**：以前 Hugging Face 只挑一家供應商，那家出錯就直接把錯誤丟回給你。現在同一次呼叫裡，會自動換下一家重試。
- **可以指定偏好**：在模型名稱後面加上後綴就行。不加就是綜合最佳；加 `:fastest` 選最快的；加 `:cheapest` 選最便宜的；加供應商名稱（例如 `:novita`）就只用那一家。
- **對話不會被換來換去**：同一段對話會盡量留在保有提示快取的那家供應商，省錢也省時間。
- **看得見錢花到哪裡**：模型頁面新增「Providers」和「Metrics」分頁，列出每家供應商過去 24 小時的價格、速度和上線率。帳單也會按供應商分開列出。不想用的供應商可以在設定裡關掉。
- **相容常見格式**：支援 OpenAI 的 Chat Completions、Responses API，以及 Anthropic 的 Messages API。Claude Code、Codex、OpenCode 等程式開發代理工具都有設定說明。

圖片、影片和聲音生成不受影響，仍然直接走 Hugging Face 的 Inference Providers，不經過 OpenRouter。

## 對使用者的意義

**一般開發者**：可以想成「一張卡搭遍所有計程車」。不用每家供應商各申請一個帳號、各管一把金鑰，也不用自己寫「這家掛了換那家」的程式。想換模型試試看，通常只要改模型名稱。

**在意成本的人**：價格沒有變，Hugging Face 不加價。PRO 使用者每月有 2 美元額度，Team 和 Enterprise 組織則是每個席位 2 美元。

**企業和團隊**：組織可以統一關掉不想用的供應商，這個設定會套用到所有記在該組織帳上的請求。需要管控資料去向的時候，這一點很實用。

**要注意的人**：如果你原本拿自己向某家供應商申請的金鑰，透過 Hugging Face 叫用語言模型，這條路現在走不通了，因為費用一律記在 Hugging Face 帳號上。你仍然可以用後綴指定供應商，或在設定裡排除其他家。圖片和影片供應商的自訂金鑰照常可用。

兩家都說這只是合作的第一步。接下來會開放 OpenRouter 帳號和 Hugging Face 連結，也會有更多種類的任務改由 OpenRouter 派送。

開源、開放權重、閉源模型，差在哪裡？

這篇用簡單的比喻說明開源模型、開放權重模型和閉源模型有什麼不同，以及各自適合哪些情況。下次選模型時，你會知道自己在取捨什麼。

**重點整理：各自適合什麼情況**

- **閉源模型**：追求最強能力、又不想自己管機器時最省事。缺點是比較貴，資料也必須交給模型公司處理。
- **開放權重模型**：便宜，可以換供應商，也可以自己架設。適合量大、重複性高、不需要最頂尖能力的工作。
- **真正的開源模型**：連訓練方法和資料都公開。適合研究、教學，或需要完整檢視模型來源的場合。

## 先搞懂「權重」是什麼

訓練 AI 模型，可以想成累積做菜的經驗。訓練過程中，模型看了大量資料，慢慢調整腦中數十億個「旋鈕」，這些旋鈕的數值就叫做權重。訓練完成之後，模型真正的本體就是這一大堆數字。

所以「公開模型」有不同的程度：只讓你吃成品，給你整份食譜，或者連食材從哪裡買、怎麼挑都告訴你。

## 三種模型的差別

**閉源模型**像只賣成品的餐廳。你只能透過網路點餐（呼叫 API），廚房在哪裡、菜怎麼做，你都看不到。你送出的資料一定會經過這家公司的伺服器。

**開放權重模型**像公開整份食譜的餐廳。權重可以下載，誰都能拿去自己煮：在自己的機器上執行，或交給任何一家供應商代為執行。不過訓練資料和完整做法通常不會一起公開。新聞裡常說的「開源模型」，嚴格來說多半屬於這一類，所以 Hugging Face 等業者會特別使用「open-weight（開放權重）」這個詞。

**真正的開源模型**連食材來源和整個做菜流程都公開，包括訓練資料、訓練程式和方法，別人理論上可以從頭重做一次。這類模型比較少見。

另外要留意授權條款。「能下載」不等於「什麼都能做」。有些模型的授權很寬鬆，有些則對商業用途或使用規模設有條件。拿來做產品之前，最好先讀過授權說明。

## 怎麼選

論能力，閉源模型目前仍然領先。在 Artificial Analysis 智慧指數上，最好的開放權重模型 Kimi K3.1 Pro 得 46 分，Claude Fable 5.2 得 65 分。

論價格，開放權重模型有明顯優勢。在 OpenRouter 上，開放模型的平均價格大約是閉源模型的四分之一。以完成單一任務來算，上面兩個模型的成本約為 3.68 美元和 26.54 美元。

也因為這樣，開放模型的用量成長得很快。在 OpenRouter 上，它的 token 占比從 2025 年 10 月的 26.8%，增加到 2026 年 9 月底的 71.7%。很多人的做法是：最難的工作交給閉源模型，大量的日常工作交給開放模型。

開放權重還有一個常被忽略的好處：不會被單一公司綁住。同一個模型可以由很多家供應商同時提供服務，某家漲價或當機就換一家。OpenRouter 這類路由服務之所以存在，正是因為開放模型有這種「多家可選」的特性。

模型的「協定」：為什麼換模型”或許"不用改程式？

這篇說明 AI 模型的 API 協定是什麼，以及為什麼現在很多服務都支援 OpenAI 或 Anthropic 的格式。了解之後你會知道，為什麼換模型時通常只需要改一個名稱。

**重點整理：API 協定為什麼存在、解決什麼問題**

- **它是什麼**：程式和模型之間「怎麼說話」的約定，例如問題要怎麼包裝、回答會長什麼樣子。
- **解決的問題**：如果每家的格式都不同，換一個模型就得重寫一次程式。大家採用共通格式之後，換模型就像換一顆同規格的燈泡。
- **對你的意義**：選工具或服務時，先看它支援哪幾種格式。支援的格式越常見，日後越好轉換。

## 用插座來理解

台灣的電器插頭都長得差不多，所以不管買哪一牌的吹風機，插上牆壁就能用。如果每家電器的插頭都不一樣，那就麻煩了。

API 協定就是 AI 模型的插座規格。你的程式要把一段對話送給模型，就得照一定的格式寫：哪一句是使用者說的，哪一句是系統設定，回應要不要一個字一個字傳回來。模型回覆時也用固定格式。雙方事先講好，才接得起來。

## 為什麼大家都學 OpenAI 和 Anthropic 的格式

OpenAI 很早就推出 Chat Completions 這套格式，大量的程式、套件和工具都照它來寫，它慢慢成為事實上的通用規格。後來 OpenAI 又推出 Responses API。Anthropic 的 Messages API 也隨著 Claude 系列普及，被許多工具採用。

其他模型供應商發現，與其要開發者學一套新格式，不如直接相容這些常見格式。結果就是：同一段程式，只要把網址和模型名稱換掉，就能改接另一家的模型。

## 實際例子：Hugging Face 的新路由

Hugging Face 這次改用 OpenRouter 來派送語言模型的請求。新的路由器同時支援 OpenAI 的 Chat Completions、Responses，以及 Anthropic 的 Messages 三種格式，不管後面實際由哪一家供應商執行模型都一樣。

所以像 Claude Code、Codex、OpenCode 這類程式開發代理工具，只要改一下設定，就能改用 Hub 上的開放模型。這就是共通協定的好處：工具和模型被拆開了，可以各自挑選。

## 要留意的地方

格式相容不代表功能完全一樣。有些進階功能，例如特定的工具呼叫方式或快取機制，各家支援的程度可能不同。換過去之後，最好實際測試一下自己會用到的功能。

模型的 16、8、4 bit 是什麼？量化一次看懂

這篇解釋開放模型常見的 16 bit、8 bit、4 bit 標示代表什麼，為什麼數字越小越省資源，以及什麼時候該用、什麼時候不該用。

**重點整理：什麼時候適合量化，什麼時候不適合**

- **適合**：想在自己的電腦或較小的顯示卡上跑模型；要大量處理、但對精準度要求一般的工作；想降低成本。
- **不太適合**：數學、程式等需要精確推理的工作；或者模型本來就小，還要再壓到很低的位元數。
- **簡單判斷**：8 bit 通常差異不大；4 bit 是省資源和品質之間常見的折衷；再往下就要小心。

## 數字代表什麼

AI 模型的本體是數十億個權重數字。每個數字用多少空間來存，就是這裡說的 bit（位元）。

可以想成用尺量東西。16 bit 像一把刻度很密的尺，可以量得很細。8 bit 的刻度比較粗。4 bit 只剩少數幾個刻度，量出來的數字只能取最接近的那一格。

把模型從 16 bit 改成用 8 bit 或 4 bit 來存，就叫做「量化」。常見的標示有 FP16、BF16（16 bit 浮點數），以及 INT8、INT4（8 bit、4 bit 整數）。

## 為什麼要量化

最直接的原因是省記憶體。簡單估算：一個 70 億參數的模型，用 16 bit 存，每個參數占 2 個位元組，光權重就大約要 14GB。改成 8 bit 約 7GB，4 bit 約 3.5GB。實際執行還需要額外空間，但比例大致如此。

這個差距決定了模型塞不塞得進你的顯示卡。原本需要專業伺服器才跑得動的模型，量化成 4 bit 之後，有機會在一般電腦上執行。記憶體用得少，通常速度也會變快，成本也會降低。

## 代價是什麼

刻度變粗，就會有誤差。多數情況下，8 bit 和 16 bit 的表現很接近，一般人很難察覺。到了 4 bit，模型偶爾會變得比較不精準，需要嚴密推理的工作特別容易受影響。再往下壓，品質就可能明顯下降。

模型本身越大，通常越禁得起量化。小模型本來就沒有多少餘裕，壓得太狠容易失常。

## 和雲端服務有什麼關係

就算你不自己架設模型，量化也跟你有關。開放模型可以由很多家供應商執行，同一個模型名稱，背後的供應商可能採用不同的精度。某一家價格特別便宜，有時候是因為用了比較低的位元數。

如果同一個模型在不同地方的表現不太一樣，精度可能是原因之一。很在意品質的話，可以留意供應商有沒有標示精度，或者用指定供應商的方式（例如 Hugging Face 新路由支援的「模型名稱:供應商」後綴），固定使用某一家。
