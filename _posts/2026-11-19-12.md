這篇把一份 Harness 實戰指南完整拆解：同一個模型、同一段 prompt，只改模型外圍的系統，被直接採用的任務就從 8 件變成 16 件。下面依原文順序，把七種常見失敗和對應修法一一講清楚。

**重點整理：這套方法什麼時候用、什麼時候不用**

- **適合**：讓 agent 自己跑一段時間、自己改程式、自己判斷「做完了沒」的場景。放手越多，Harness 越重要。
- **不需要**：快速、低風險的一次性小任務。一個 prompt 加一個模型就夠了，原文稱為 Level 0。
- **判斷原則**：親眼看過某種失敗之後，才加上對應的那一層。Harness 要比它管的問題小。
- **要定期修剪**：有些規則是在彌補現在模型的弱點。模型變強之後，這些規則會變成累贅。

## 同樣的錯，換了 prompt 也沒用

原文作者用 Claude Opus 5.5 當 coding agent，讓它維護一個追蹤鏈上活動的小服務。他連續三週每天早上打開 repo，看到的都是同樣幾種狀況：功能號稱完成，但測試一片紅；一個他從沒提過的設定檔被改掉；有一晚某個失敗的 API 呼叫被重試了 41 次，直到預算上限才停下來。

他的反應和大多數人一樣：改 prompt、換模型、塞更多文件。結果錯誤照舊。

他的結論是，prompt 從來不是問題，模型多半也不是。Opus 5.5 能做的事比它表現出來的多，卡住它的是包在外面的那一圈東西，也就是 Harness。

可以想成請一位很聰明的新同事。他做不好，未必是腦袋不夠，可能是你沒告訴他做到什麼程度算交差、沒給他公司的平面圖、也沒說哪些東西不能碰。這時候換一個更聰明的人來，結果多半一樣。

## 公開證據：模型沒換，成績大跳

原文舉了兩個例子。

**LangChain**：自家 coding agent 在 Terminal Bench 2.0 的分數從 52.8% 拉到 66.5%，排名從三十名以外進到前五。模型沒換，改的只有 prompt、工具和 middleware，也就是模型周圍的系統。

**OpenAI**：三位工程師推動約 1,500 個 pull request，進到一個每行程式都由 Codex 寫的 repo。這個例子在延伸閱讀〈用 OpenAI Codex 的實驗看懂 Harness：工程師的工作從寫程式變成蓋環境〉裡有詳細說明。

兩個例子講的是同一件事：真正的槓桿在模型外面的系統。

## 作者自己的對照實驗

作者從自己的待辦清單挑了 20 件真實任務，有修 bug、小功能，也有幾個重構。模型、prompt、機器都相同，各跑一次。

- **A 組**：只把 prompt 丟進 repo，其他什麼都沒有。
- **B 組**：同樣的 prompt，加上他用一個週末搭的 Harness，內容包括：每個任務一份附「done when」的小契約、一份 40 行的地圖檔（取代原本一大坨文件）、宣告完成前必須通過的測試關卡、最多重試三次的上限，以及一份規定能碰什麼、不能碰什麼的規則檔。

結果如下：

| 項目 | A 組 | B 組 |
|---|---|---|
| 不用他動手就能採用的任務 | 8 / 20 | 16 / 20 |
| 失控的重試迴圈 | 5 次 | 0 次 |
| 每件被採用任務的平均成本 | 約 4.10 美元 | 約 1.60 美元 |
| 每天花在盯場的時間 | 約 2 小時 | 約 25 分鐘 |

模型一次都沒換，prompt 的措辭也沒動。所有改善都來自外圍。

## Agent = 模型 + Harness

這是全文的核心公式。

- **模型**負責推理，提出「下一步該做什麼」。
- **Harness** 負責其他所有事：模型看得到什麼、能用哪些工具、跨對話記得什麼、怎樣算完成、什麼絕對不能做、出錯時怎麼辦。

同一個模型放進聊天框，只會回答問題。放進一個有終端機、測試、專案筆記、權限和審查者的 repo，就能做真正的工作。它的智力沒有改變，改變的是它所處的環境。

## 先找出是哪一層壞掉

動 prompt 之前，先問：壞的是哪一層？原文給了一張快速診斷表：

- **聽錯需求**：prompt 問題，重寫指令。
- **講得很順，但內容錯誤或過時**：context 問題，缺了對的資訊，或被錯的資訊淹沒。
- **沒證據就說做完、做了危險的事、換個對話就失憶**：Harness 問題，模型周圍少了某個東西。
- **一直重複同一招**：loop 問題，沒有機制決定何時停下或換方法。
- **好幾個 agent 重工或互撞**：graph 問題，沒人設計它們怎麼協作。

作者也說明，這五層只是方便思考的模型，不是官方標準。重點在習慣：把 prompt 寫長，只能修第一層，但大部分的痛都發生在下面幾層。就像車子發不動，你一直換更貴的汽油，問題卻可能是電瓶沒電。

## 七種常見失敗與修法

### 1. 「它做的不是我要的」：開工前先寫契約

「把註冊流程改好一點」這種話，身邊坐著一個人時還行，交給自動執行的 agent 就像擲硬幣。

修法是把需求變成一個有邊界的小物件，例如：

- **目標**：降低註冊流程的流失
- **限制**：認證機制不動，不改資料表結構
- **交付物**：一個可以審查的 pull request
- **完成條件**：測試通過、分析事件有觸發、桌機和手機流程都通過審查
- **需要核准**：任何會碰到正式環境的事

最關鍵的是「done when」那一行。少了它，agent 可能偷偷解一個比較簡單的版本，然後一本正經地回報成功。

打個比方：你叫人「把房間整理一下」，他把衣服塞進衣櫃就說好了。如果你說「地板上看不到東西、床鋪好、垃圾倒掉才算完成」，就沒有模糊空間。作者還強調一點：契約裡要寫明什麼情況該停下來問人。沒有這條指令的 agent，永遠會選擇用猜的。

### 2. 「它在我的程式碼裡迷路」：給地圖，不要給說明書

出錯之後，直覺反應是塞更多 context。但 context 不是倉庫，而是注意力預算，倒得越多，它理解得越少。

OpenAI 早期也得到同樣的教訓：一份指向深入資料的簡短指南，效果比一份巨大的指令檔好。所以只保留一個小小的根目錄檔案（AGENTS.md、CLAUDE.md，看你用什麼工具），寫清楚架構、測試、產品規則、資安各放在哪裡。任務需要時，再讓 agent 自己打開詳細文件。

就像帶新人逛公司，你不會叫他先讀完五百頁員工手冊，而是告訴他：「會計在三樓，IT 在二樓，有事去找。」根目錄檔案應該一個螢幕就看完，不寫解釋、不寫歷史、不寫風格論文。目標不是讓它知道最多，而是讓它在動手那一刻拿到最有用的訊號。

### 3. 「它說做完了，其實沒有」：用證據當完成的門檻

「做完了」不是事實，只是模型的另一句輸出。作者在 A 組裡，agent 回報 20 件全部完成，實際跑測試只有 8 件站得住腳。

修法是把宣稱換成環境可以執行的檢查：

- 「bug 修好了」：原本失敗的測試現在通過。
- 「頁面能用」：瀏覽器實際跑完整個流程。
- 「資料正確」：數值和來源對得上。
- 「任務完成」：每一項驗收條件都通過。

優先用確定性的工具，例如型別檢查、linter、測試。編譯器能證明的事，不要叫另一個模型去猜。作者的整個關卡就是一支腳本：沒印出 `GATE: PASS`，不管 agent 怎麼說，都不算完成。

第二步是把建造者和驗收者分開。自己檢查自己的作品，很容易帶著同樣的盲點，就像自己校對自己的作文，錯字常常看不見。驗收者該問的不是「看起來好不好」，而是「什麼情況會讓它不合格」。這樣審查就從「確認沒問題」變成「想辦法把它弄壞」。

### 4. 「它做了我沒批准的事」：把權限放在模型外面

跟 agent 說「絕對不要合併到 main」只是許願，設成受保護分支才是一道牆。

依照「多難復原」把動作分三類：

- **安全、可復原**（讀取、搜尋、跑測試、改工作分支）：放手讓它做，但留下紀錄。
- **外界看得到**（寄信、部署、付款）：需要核准。
- **難以復原**（刪資料、換金鑰、全面發布）：整條路直接封死。

封死和「門檻很高」不一樣。門檻在有人趕時間時會被調低，封死的路就是封死。

這像家裡的藥櫃。跟小孩說「不要亂吃藥」是一回事，把藥櫃鎖起來是另一回事。原文的說法是：模型建議，Harness 決定，工具執行。

### 5. 「它一直重試同一件事」：先分類失敗，再設上限

「失敗了就再試一次」等於為同一個錯誤重複付錢。

LangChain 觀察到 agent 會掉進所謂的 doom loop，對同一段修改做微小變化，一再重來。他們的修法放在 Harness 裡：用一段 middleware 偵測同一個檔案被反覆修改，就提醒 agent 重新想想做法。

依失敗類型給不同處理：

- **逾時**：等一下再試。
- **參數錯誤**：修正工具呼叫。
- **缺資訊**：去把資訊找來。
- **測試失敗**：看失敗的行為，改程式碼，絕不改測試。
- **權限被拒**：問人。
- **同樣的錯連續兩次、什麼都沒變**：停下來。

每個迴圈都要限制次數、時間和花費，「試三次就升級給人處理」是合理的預設。三次之後還是紅的，通常是計畫本身錯了，而迴圈看不到計畫。

就像你忘了密碼，第三次輸錯就該停下來想想是不是記錯帳號，而不是繼續亂試到被鎖。作者加上三次上限之後，41 次重試的那種夜晚再也沒出現。agent 在第三次停下，留了一張紙條列出它試過什麼，那是他第一次從 agent 身上拿到真正有用的除錯報告。

### 6. 「它忘了我們的決定」：把狀態存在對話外面

聊天紀錄是很糟的資料庫。context 會滿、對話會當掉、工作會交給全新的 agent。

修法是在工作旁邊放一個小小的狀態檔，記錄目前進行到哪一步、做了哪些決定和原因、產出了什麼、還有哪些風險、下一步是什麼。新對話開始時讀這個檔，不靠一段失真的轉述。

這就像兩種同事的差別：一個交接時留下交接單，另一個說「都在我腦子裡」。

### 7. 「同樣的錯犯了兩次」：把每個教訓變成基礎設施

這一條的效益會累積，所以最重要。多數人只修這次的輸出，Harness 工程師修的是這一類錯誤。

假設 agent 讓 UI 程式直接查資料庫。你可以把規則寫進 prompt；好一點是寫進指南並附上理由；最好是加一個 lint 檢查，只要 UI 程式引用資料層，build 就失敗。這樣規則就不需要任何人或模型記得。

進程是四步：先說明，再列成檢查清單，再自動化檢查，最後強制執行。每個反覆出現的錯，都應該往這個階梯下方推一步，直到環境本身記住教訓，模型不用記。

判斷指南寫得好不好的方法：每一行都應該對得上一次真實出過的事。指不出事件的那一行，大概是雜訊。作者的指南檔一開始 6 行，三週後 31 行，每一行他都說得出背後是哪一晚。例如「永遠不要改範例 env 檔」，是因為 agent 曾經「好心」填進看起來很像真的數值；「每次 commit 前先跑 formatter」，是因為他審空白字元審到煩了。

## 比你想的更小地開始

第一天不需要什麼編排平台。原文分了四個等級：

- **Level 0**：一個 prompt 加一個模型，適合快速、低風險的任務。
- **Level 1**：加上契約、簡短地圖、幾個定義清楚的工具。
- **Level 2**：加上存起來的狀態、真正的檢查、有邊界的迴圈。
- **Level 3**：加上權限、紀錄追蹤、復原路徑、人工核准關卡。

原則是看過某種失敗，才加上防它的那一層。作者也老實提醒：Harness 有一部分是在彌補今天模型的不足，模型進步後，這些部分會變成累贅。從不修剪的 Harness，會變成下一個要除錯的對象。

## 放手之前的檢查清單

給 agent 真正的自主權之前，問自己這十題：

1. 開工前有沒有定義什麼叫「完成」？
2. 它能不能不載入全部資料就找到對的 context？
3. 每個工具有沒有清楚的用途和清楚的錯誤訊息？
4. 決定有沒有存在對話外面？
5. 完成有沒有要求證據？
6. 檢查的是不是建造者以外的角色？
7. 危險動作是被規則擋住，還是只被一句話擋住？
8. 每個迴圈有沒有重試上限和預算？
9. 當掉之後能不能接著跑？
10. 每次失敗有沒有留下一條規則、一個測試或一道檢查？

如果好幾題答案是否定的，換更聰明的模型也救不了，只會讓它更快、更貴地失敗。

## 真正的轉變

Prompt 問的是：我該跟模型說什麼？Context 問的是：它現在該看到什麼？Harness 問的是：要什麼樣的系統，才能讓它動手、檢查自己、從失敗中恢復，而且不越界？

模型每幾個月就換一代，但你搭起來的契約、測試、地圖、狀態和權限會留下來。每把一次失敗變成基礎設施，下一次就跑得更好。競爭優勢正在從 prompt 移到模型外圍的系統。
