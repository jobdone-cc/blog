用 OpenAI 一個由 Codex 寫出全部程式碼的實驗，說明什麼是 Harness，以及為什麼 agent 卡關時，該修的常常是環境而不是模型。

## 三個工程師、約 1,500 個 PR

這個案例出自一篇談 agent Harness 的 X 長文。文中提到，OpenAI 描述過一個實驗：三位工程師推動了大約 1,500 個 pull request，進到一個每一行程式都由 Codex 寫的 repo。

有意思的是開頭卡住的那段。進度一開始很慢，他們的診斷不是「模型太弱」，而是「環境沒有交代清楚」。接著工程師的工作重心就轉了：從自己寫程式，變成設計環境、講清楚意圖、建立回饋迴圈。

## Harness 到底是什麼

可以用一個公式記：**Agent = 模型 + Harness**。

模型負責想，它會提出「下一步該做什麼」。Harness 是模型以外的一切：它看得到什麼、能用哪些工具、跨對話記得什麼、怎樣算完成、什麼不准做、出錯時怎麼辦。

用廚房來比喻。模型是一位手藝很好的廚師，Harness 是整間廚房：食材放在哪、哪把刀能用、瓦斯開關在哪、出餐前誰試味道、哪些食材過敏的客人不能碰。把頂尖廚師丟進一間東西亂放、沒有菜單、沒人試菜的廚房，他照樣會出錯。這時候換一個更厲害的廚師沒什麼用，該做的是把廚房整理好。

OpenAI 這三位工程師做的就是整理廚房。拆開來看有三件事：

- **設計環境**：讓 Codex 進到 repo 時，知道東西在哪、有哪些工具、規則是什麼。
- **講清楚意圖**：告訴它要做什麼、做到什麼程度算完成。
- **建立回饋迴圈**：讓它做完之後，能從測試或檢查得知自己對不對，而不是只靠自己說「好了」。

## 一個具體的教訓：短指南勝過大文件

長文還提到 OpenAI 早期的一個發現：一份簡短、指向深入資料的指南，效果比一份巨大的指令檔好。

這個發現有點違反直覺，因為我們通常以為資訊越多越好。但對 agent 來說，context 比較像注意力預算，不是倉庫。就像你問路，對方給你一本五百頁的城市百科，不如給你一張標好重點的簡圖，需要細節時再去查。所以做法是保留一個小的根目錄檔案，只寫架構、測試、產品規則、資安各在哪裡，細節讓 agent 需要時再打開。

## 這個案例想說的事

同一篇長文也引用了 LangChain 的例子：模型不換，只調整周圍系統，基準分數就從 52.8% 升到 66.5%。兩家公司說的是同一件事：槓桿不在模型本身，在模型周圍的系統。

這也解釋了為什麼 OpenAI 那三位工程師的角色會轉變。當寫程式這件事交給 agent，人的價值就移到另一個位置：決定 agent 活在什麼樣的環境裡。模型每幾個月就換一代，但環境、規則和回饋迴圈會留下來，而且越用越好。
